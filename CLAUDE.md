## Repository layout

The Astro project lives in `page/`, not at the repo root. All `npm` commands must be run from `page/`. The repo root only holds `.github/workflows/` and a stale `.quarto/` gitignore entry left over from a previous Quarto/R version of the site.

## Commands

Run from `page/`:

- `npm install --legacy-peer-deps` — install deps (CI uses `--legacy-peer-deps`; use it locally too to avoid divergence)
- `npm run dev` — dev server at `localhost:4321`
- `npm run build` — production build into `page/dist/`
- `npm run preview` — preview the built site
- `npm run astro check` — type-check `.astro` files (no separate test/lint script is configured)

## Architecture

**Stack:** Astro 5 (static, no SSR adapter) + Tailwind 3 (`darkMode: 'class'`) + MDX + sitemap. TypeScript is `astro/tsconfigs/strict`. The site URL `https://julianusor.github.io` is hardcoded in `page/astro.config.mjs` and is required for canonical URLs, OG images, and the sitemap.

**Content collections drive the blog.** `src/content/config.ts` defines a `blog` collection with a Zod schema (`title`, `author`, `date` required; `modified`, `categories`, `image`, `description` optional). Adding a post means dropping an `.mdx` file into `src/content/blog/` with that frontmatter — no other registration is needed. The dynamic route `src/pages/blog/[...slug].astro` enumerates the collection via `getStaticPaths` and renders through `BlogPostLayout`. Post images referenced as `/posts/...` resolve from `public/posts/`.

**Layouts:** `BaseLayout.astro` is the chrome (Navbar, Footer, OG/Twitter meta, RSS link, favicon, fonts, the pre-paint theme script, and the `max-w-6xl` content column) used by every standalone page. There is no default social image: `og:image` is only emitted when a page passes one, and the Twitter card falls back to `summary`. `BlogPostLayout.astro` wraps `BaseLayout` with post-specific rendering (including a "Posted/Updated" date row driven by the optional `modified` frontmatter) and is only used by the `[...slug]` route. New top-level pages should use `BaseLayout` directly.

**Visual style:** Minimal and high-contrast, in the vein of Palantir/Coinbase. Structure comes from 1px hairline borders (`border-ink-200 dark:border-ink-800`), never from shadows or rounded corners — avoid `rounded-*` and `shadow-*` on new surfaces. The palette is the custom `ink-50…950` neutral scale in `tailwind.config.mjs`, with `accent` (`#1652F0`) used sparingly for hover and links. Body copy is Inter; metadata, labels, and eyebrows are `font-mono` at ~10–11px, uppercase, with wide tracking. Card grids are built as `grid gap-px bg-ink-200` so the background shows through as hairlines between cells.

**Pages other than the blog** (`about-me`, `food-prices`, `real-estate`) are plain `.astro` files in `src/pages/`. RSS is generated by `src/pages/rss.xml.js`.

## Deployment

`deploy-astro.yml` is the only workflow and the only deploy path. On push to `main` it builds `page/` and publishes the artifact via `actions/deploy-pages`. **The Pages source is set to "GitHub Actions"** in repo settings — not a branch. Do not add a workflow that publishes to a `gh-pages` branch: it would be dead weight, and the built-in `pages-build-deployment` (Jekyll) job would run against it and fail, since an Astro build needs `.nojekyll` for its `_astro/` directory.

Because the deploy runs `cd page && npm ci --legacy-peer-deps && npm run build`, anything outside `page/` is ignored by the build.

If a push produces no workflow run at all (check the Actions tab), the cause is repo- or account-level — Actions disabled in settings, or a billing block — not the workflow file.
